MUSK more_obstacles 最终思路与修改说明
======================================

本文整理当前 more_obstacles 场景的整体实现思路，以及最终保留下来的主要代码
和配置修改。


一、基本思路
------------
目标不是手写轨迹，而是在 MUSK 原有架构中接入 EGO-Planner：

1. MUSK 继续负责：
   - 启动 PX4 SITL、Gazebo、MAVROS。
   - 管理每架无人机的状态机。
   - 执行 INIT、TAKEOFF、PREPARE、GUIDANCE 等阶段。
   - 接收 EGO 输出并转换成 PX4/MAVROS 可执行的控制命令。
   - 发布 RViz 可视化和调试日志。

2. EGO-Planner 负责：
   - 接收每架无人机的 odometry。
   - 接收由圆柱障碍物采样出的点云地图。
   - 根据每架无人机的目标点规划路径。
   - 输出 quadrotor_msgs/PositionCommand。

3. more_obstacles 场景中：
   - 5 架无人机从 x=-4.8 一侧起飞。
   - y 方向分布为 -4.8、-2.4、0.0、2.4、4.8。
   - 目标点在 x=10.0 另一侧，y 与各自起点对应。
   - 高度统一为 1.2 m。
   - 中间布置多根圆柱障碍物，Gazebo 中有真实 collision，RViz 中有 marker 显示。

4. 控制链路：
   Gazebo/PX4/MAVROS -> P230 -> MUSK SingleRun -> EGO odom/cloud
   EGO pos_cmd -> SingleRun -> 速度控制 -> MAVROS setpoint_raw/local -> PX4


二、场景配置修改
----------------
文件：
guidance/ros_ws/src/multi_uav_formation/scenes/more_obstacles.json

主要内容：
- number = 5
- leaders = 1
- head = 1
- takeoffPointENU / preparePointENU 扩展为 5 架。
- egoPlanner.goalsENU 扩展为 5 个目标点。
- maxVel、maxAcc、planningHorizon 等 EGO 参数写入 egoPlanner 字段。
- obstacleData 中定义多根圆柱障碍物。
- 增加 mavrosLocalOffsetENU，用于修复三号机 MAVROS local frame 与任务坐标
  不一致的问题。

当前三号机补偿：
  raw MAVROS 初始位置约为 (0,0,z)
  任务坐标期望为 (-4.8,0,z)
  因此 uav3 offset = [-4.8, 0.0, 0.0]


三、Gazebo world 修改
--------------------
文件：
guidance/ros_ws/src/multi_uav_formation/worlds/more_obstacles.world

作用：
- 定义 more_obstacles 使用的 Gazebo 世界。
- 将 JSON 中的障碍物同步为 Gazebo 静态圆柱模型。
- 每个圆柱包含 visual 和 collision。

要点：
- RViz marker 只负责显示，不会产生物理碰撞。
- Gazebo world 中的 collision 才是真正的物理障碍。


四、PX4/MAVROS 五机启动
----------------------
文件：
guidance/ros_ws/src/multi_uav_formation/launch/multi_uav_mavros_sitl.launch

修改：
- 从原有数量扩展到 uav1-uav5。
- 每架无人机使用不同 namespace、ID、UDP/TCP 端口。
- spawn x/y 与 more_obstacles.json 中的起点对应。

五架起点：
  uav1: (-4.8, -4.8)
  uav2: (-4.8, -2.4)
  uav3: (-4.8,  0.0)
  uav4: (-4.8,  2.4)
  uav5: (-4.8,  4.8)


五、EGO 五机启动
----------------
文件：
guidance/ros_ws/src/multi_uav_formation/launch/ego_more_obstacles.launch

修改：
- 启动 drone_0 到 drone_4 的 EGO planner/traj_server。
- 每个 drone 对应一个目标点。
- 每个 drone 的目标高度统一为 1.2。

话题对应关系：
  uav1 -> drone_0
  uav2 -> drone_1
  uav3 -> drone_2
  uav4 -> drone_3
  uav5 -> drone_4


六、SingleRun.py 修改
--------------------
文件：
guidance/ros_ws/src/multi_uav_formation/multi_uav_formation/SingleRun.py

SingleRun.py 是本次改动的核心。原来的 SingleRun 主要按 MUSK 自己的状态机
做起飞、准备点、编队/引导、返航和降落；本次改写后，它变成了 MUSK 和
EGO-Planner 之间的桥接层：上游接 PX4/MAVROS 的真实状态，下游给 EGO 提供
odom/cloud，再把 EGO 的规划输出转换回 MAVROS 速度控制。

相比原版 SingleRun.py，本次主要新增/改写了这些东西：
- 新增 egoPlanner 配置读取：从 scene JSON 读取 enabled、goalsENU、点云分辨率、
  触发延迟、目标容差、控制增益等参数。
- 新增 EGO 运行状态变量：egoPlannerAvailable、egoPlannerTriggered、
  egoGoalReached、egoLastCommand、egoGoalPointENU、egoCloudPoints 等。
- 新增 MAVROS local 坐标补偿接入：读取 mavrosLocalOffsetENU，并传给 P230。
- 新增 setupEgoPlannerBridge()：创建 EGO 所需的 odom/cloud/trigger publisher，
  以及 pos_cmd subscriber。
- 新增 egoPositionCommandCallback()：缓存 EGO traj_server 输出的
  PositionCommand。
- 新增 buildEgoObstacleCloud()：把 JSON 中的圆柱障碍物采样成 PointCloud2 点云。
- 新增 publishEgoPlannerInputs()：持续向 EGO 发布当前无人机 odom 和障碍物点云。
- 新增 publishEgoStartTrigger()：进入 GUIDANCE 后触发 EGO 开始规划。
- 新增 projectVelocityAwayFromObstacles()：在 MUSK 层做轻量几何避障保护。
- 新增 guardedVelocityToPointENUControl() 和 guardedConstantVelocityLineENUControl()：
  给点目标/直线跟踪速度加障碍物保护。
- 新增 holdCurrentPosition()：遇到安全阻断或缺少有效 EGO 指令时发送零速度保持。
- 改写 toStepTakeoff() 和 stepTakeoff()：从直接飞向 takeoffPoint 改为就地垂直起飞。
- 改写 toStepGuidance()：EGO 可用时切换到速度控制模式，并重置 EGO trigger/goal 状态。
- 改写 stepPrepare()：使用 SingleRun 自己的速度闭环函数，方便统一记录和保护。
- 改写 stepGuidance()：优先进入 EGO guidance；EGO 不可用时才走原 MUSK fallback。
- 新增 stepEgoPlannerGuidance()：把 EGO 的 PositionCommand 转成 MAVROS 速度指令。
- 改写目标到达逻辑：到达 egoPlanner.goalsENU 后保持最终目标点悬停，不再自动返航。
- 改写 formationTime 超时逻辑：EGO 模式下超时不强制 BACK/LAND。
- 改写 stepBack()：返航速度也经过障碍物保护。
- 改写主循环 run()：每轮控制前持续发布 EGO 输入。

1. 初始化阶段重写
   - 保留原有 scene JSON 加载方式。
   - 新增读取 egoPlanner 字段：
     enabled、goalsENU、maxVel、maxAcc、planningHorizon、cloudResolution、
     obstacleHeight、commandTimeout、triggerDelay、positionGain、
     velocityGain、goalTolerance 等。
   - 新增 egoPlannerEnabled、egoPlannerAvailable、egoPlannerTriggered、
     egoGoalReached、egoLastCommand、egoGoalPointENU 等运行时状态变量。
   - 从 mavrosLocalOffsetENU 读取每架无人机的 MAVROS local 坐标补偿，并传给
     P230。这样 SingleRun 内部始终使用“任务坐标”，不直接暴露有偏移的 raw
     MAVROS 坐标。

2. P230 初始化方式变化
   - 原来：
     P230(name=f'uav{self.number}')
   - 现在：
     P230(name=f'uav{self.number}', localOffsetENU=localOffsetENU)
   - 这一步使 SingleRun、RViz、EGO 看到的是补偿后的统一 ENU 坐标。

3. 新增 setupEgoPlannerBridge()
   - 这个函数负责把 SingleRun 接到 EGO-Planner。
   - 如果 scene JSON 中 egoPlanner.enabled=false，则不启用 EGO 桥接。
   - 如果缺少 quadrotor_msgs、PointCloud2 等依赖，则打印信息并回退。
   - 每架无人机按编号建立对应话题：
     uav1 -> drone_0
     uav2 -> drone_1
     uav3 -> drone_2
     uav4 -> drone_3
     uav5 -> drone_4
   - 发布：
     /drone_i_visual_slam/odom
     /drone_i_pcl_render_node/cloud
     /traj_start_trigger
   - 订阅：
     /drone_i_planning/pos_cmd

4. 新增 EGO 输入发布
   - publishEgoPlannerInputs() 会把当前无人机状态发布给 EGO。
   - odom 中的位置、速度来自 P230 补偿后的 mePositionENU/meVelocityENU。
   - 这意味着 EGO 规划坐标、RViz 显示坐标、MUSK 控制状态机坐标保持一致。
   - 该函数在主循环里每轮调用，而不是只在 GUIDANCE 阶段调用。
   - 这样 EGO 不会在无人机 TAKEOFF/PREPARE 时长期处于 no odom。

5. 新增障碍物点云生成
   - buildEgoObstacleCloud() 读取 more_obstacles.json 中的 obstacleData。
   - 每个圆柱按 cloudResolution 采样成三维点云。
   - 点云发布到 /drone_i_pcl_render_node/cloud。
   - EGO 用这些点云构建局部地图并进行避障。

6. 新增 trigger 逻辑
   - publishEgoStartTrigger() 在 GUIDANCE 阶段延迟 triggerDelay 后发布。
   - 发布一次后 egoPlannerTriggered=true，避免重复触发。
   - trigger 的位置使用当前补偿后的任务坐标。

7. TAKEOFF 状态改写
   - 原逻辑可能直接飞向 takeoffPointENU，因此如果当前位置和配置起飞点不一致，
     起飞时会产生明显横向运动。
   - 新逻辑在进入 TAKEOFF 时记录当前 x/y，只把 z 拉到目标高度：
     takeoffVerticalPointENU = [current_x, current_y, target_z]
   - stepTakeoff() 中使用 velocityToPointENUControl() 做就地垂直起飞。
   - 所有无人机完成 TAKEOFF 后，head 才推进到 PREPARE。
   - 这样起飞阶段不再承担横向归位任务，横向移动留给 PREPARE。

8. PREPARE 状态改写
   - PREPARE 阶段负责把无人机送到各自 preparePointENU。
   - 使用 SingleRun 自己的 velocityToPointENUControl()，便于统一记录 self.u
     和后续扩展避障保护。
   - 到达 preparePointENU 且速度足够低后，标记该状态完成。
   - head 负责等待所有无人机完成 PREPARE，再进入 GUIDANCE。

9. GUIDANCE 状态改写
   - stepGuidance() 现在先判断 EGO 是否可用。
   - 如果 EGO 可用，进入 stepEgoPlannerGuidance()。
   - 如果 EGO 不可用，才走原来的 MUSK fallback guidance。
   - 这让 more_obstacles 场景优先使用 EGO-Planner，而不是继续执行原来的
     简单直线/队形逻辑。

10. 新增 stepEgoPlannerGuidance()
   - 每轮先尝试发布 EGO trigger。
   - 然后检查 safetyModule()。
   - 如果最近收到的 PositionCommand 没超时，则取 EGO 输出：
     posENU = cmd.position
     velENU = cmd.velocity
   - 用位置误差和速度误差生成最终速度命令：
     controlVel = velENU
                + positionGain * (posENU - currentPosition)
                + velocityGain * (velENU - currentVelocity)
   - 再经过 projectVelocityAwayFromObstacles() 做本地保护。
   - 最后通过 P230.velocityENUControl() 发给 MAVROS。
   - 如果 EGO 暂时没有新命令，则悬停/靠近 preparePointENU，避免盲飞。

11. 目标到达与悬停逻辑
   - 读取 egoPlanner.goalsENU 作为每架无人机最终目标。
   - 当当前位置接近 egoGoalPointENU 且速度足够低时：
     egoGoalReached = True
     stateFinished = True
   - 之后不再进入 BACK/LAND，而是持续对最终目标点做速度闭环：
     velocityToPointENUControl(self.egoGoalPointENU, yaw)
   - 这保证无人机穿越障碍物林后在对面对应点悬停。

12. formationTime 超时逻辑改写
   - 原始 MUSK 逻辑中，formationTime 到期后可能进入 BACK 或 LAND。
   - more_obstacles 需求是到达目标点后悬停。
   - 因此 EGO 模式下 formationTime 到期只打印提示，不再强制返航。

13. 本地几何避障保护
   - 新增 projectVelocityAwayFromObstacles()。
   - 它基于 JSON 里的圆柱中心、半径和 obstacleClearance，检查当前速度是否会把
     无人机推入障碍物安全半径。
   - 如果会，则去掉朝向障碍物内部的速度分量，并加入少量向外推开的速度。
   - 这不是主规划器，只是 EGO 之外的最后保护层。

14. holdCurrentPosition()
   - 新增统一的“原地保持”函数。
   - 当 safetyModule 阻止继续飞行或缺少有效指令时，发送零速度，而不是直接
     toStepBack()。
   - 这样避免安全保护触发后无人机突然返航或降落。

15. 主循环改写
   - 在 run() 主循环中，每轮控制状态机前调用 publishEgoPlannerInputs()。
   - 执行顺序变成：
     更新日志/显示 -> 发布 EGO 输入 -> 状态机控制 -> 发送 MAVROS heartbeat/setpoint。
   - 这样 EGO 始终能看到最新状态，MUSK 也能持续接收 EGO 输出。

总结：
SingleRun.py 的角色从“只执行 MUSK 自己的引导逻辑”改成了“状态机 + EGO 桥接 +
控制转换 + 最终目标保持”。这也是 more_obstacles 能在 MUSK 架构里调用
EGO-Planner 的关键。
